User 2026-10-11 (from a friend's suggestion), "store away for later":
- Couples auto-generate their own wedding mailbox FROM Tulle (e.g. name@<wedding-domain>), used for all vendor contact.
- Possibly build a wedding website for them off the same identity.
- Main value: Tulle negotiates FOR them from that mailbox and gets real pricing; becomes a Tulle "negotiation" tool using an AI vendor.
- Side effect worth noting when it is resumed: every vendor reply = a fresh, real quote -> feeds the pricing corpus (the core asset), and gives a reason to stay through the 12-18 month planning period (retention gap: ~5% of sign-ups return in week 1, [[project_engagement_baselines_2026-10-09]]).
- Related signal: onboarding goals question has option contact_negotiate ("Contact vendors and negotiate better prices") live from 10-11 - read its share before scoping ([[project_nps_survey]]). Assistant users already ask cost/negotiation-style questions ([[project_ai_recommendation_engine]]).
- Open questions to answer before any build: deliverability/spam reputation of a new sending domain (welcome mail already lands in spam, [[project_welcome_email_spam]]); vendor consent/disclosure that an AI is negotiating; who is liable for commitments; inbound parsing + storage of PII; cost per couple.
**How to apply:** do not build or scope unless the user brings it back; when they do, start with the contact_negotiate share and a demand check.
- 10-11 feasibility answer given: NOT a real mailbox per couple (Workspace/M365 ~$6-7/user/mo). One separate wedding domain + catch-all; inbound via Postmark/Mailgun/SendGrid/SES -> Xano, inbox UI in Tulle; outbound via same, signed. ~fractions of a cent/email (UNPRICED estimate). Must be a SEPARATE domain from tulletogether.app (protect transactional deliverability), SPF/DKIM/DMARC + warm-up, per-address send limits. Websites: one template page keyed by slug (could be a WeWeb page), custom domains later; commodity (Zola/Knot/Joy/Minted free) - value is the shared identity + negotiation. Suggested first test: concierge (manual) negotiation for 10-20 couples from one test domain.
- 10-11 user concern: vendors get suspicious seeing many requests from one tulle.wedding domain. My answer: many domains = WORSE (no reputation, rotation is a spam tactic). Options: (1) openly branded platform relay like The Knot/WeddingWire messaging (real risk = vendors recognise Tulle as the price-comparison site and quote higher/refuse); (2) couple's own Gmail/Outlook via OAuth - vendor sees the couple; Gmail restricted scopes need Google verification + paid CASA security assessment (UNVERIFIED cost/time; weeks-months, ~thousands/yr), Microsoft easier. Cheapest first test: concierge negotiation from couples' OWN email (CC/forward a Tulle address), 10-20 couples, compare quotes + vendor reaction.
- 10-11 DECISION (user + me): NO wedding websites - commodity (Zola/Knot/Joy/Minted free; RSVP, guest list, registry, travel, themes...), zero demand signal in Tulle data (0 assistant msgs, 0 #feedback, 0 searches). Lean into pricing instead; retention ideas that fit: "Is this quote fair?" (upload/paste a quote vs comparable real prices - also grows the corpus, first step toward negotiation), budget from saved vendors' real prices, P/E in the assistant, shareable partner shortlist. Negotiation-from-inbox idea stays PARKED separately.
