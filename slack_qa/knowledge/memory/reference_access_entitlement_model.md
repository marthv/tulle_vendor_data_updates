Paid-access entitlement model (workspace 1), verified 2026-07-22:

- **Entitlement is stored ONLY as two fields on `user` (table 1):** `date_until_access` (date) and `forever_access_purchased` (bool), plus `total_payments`/`total_amount_paid`. **There is NO plan/tier/filter-access column anywhere.** So "filters = $100+ tier" is a pure WeWeb frontend gate with no dedicated backend field — it can only be inferred from `forever_access_purchased` (the only boolean entitlement signal).
- **Stripe webhook = ep 30** (group 7 stripe_checkout, `/webhooks`). Grants access keyed on `$session.client_reference_id` → user_id. Maps `metadata.weeks` exact strings ("1 week","2 weeks","4 weeks","6 weeks","12 weeks","24 weeks","forever weeks") to a seconds offset added to `date_until_access` (stacks on existing future date). "forever" → date 2999 + forever flag. **Silent-failure risk:** if `metadata.weeks` is missing/typo'd AND `metadata.type` != "concierge", the whole branch is skipped — NO access, NO payment-log row, NO error, returns `{status:ok}`. If `client_reference_id` is null → user_id 0 → payment IS logged but db.edit no-ops (paid, zero access).
- **LIVE pricing as of 2026-08-16: 1 week=$30 · 4 weeks=$55 · forever=$129** (confirmed against the Stripe payment links AND the /pricing card grid, which agree). Older Payment Log rows show 4 weeks=$50 and forever=$119 — those are the PREVIOUS prices; forever rose to a flat $129 on 2026-08-12. CLAUDE.md's "$75 lifetime" is stale. Amounts in table 16 include NY sales tax (~8.875%), so $55 lands as 59.88.
- **`/purchase-complete` told EVERY buyer "No recent purchase found" (fixed 2026-08-16).** Its onload action `POLL_ACCESS_SUMMARY` read the token as `pluginVariables['f5856798-…']['user']['authToken']` — but the plugin's `user` is the auth/me payload and has no `authToken`, so the guard returned on line 2 and `fetch` never ran (**ep216 had ZERO requests in history — that was the tell**). Payment, access grant and payment-log row were all fine. Suspected cause of the ~6 duplicate payments/30d. **There is NO verified way to read the Xano plugin's token in custom JS** — the only other authed `fetch` in the project (`79c62d01` `__FETCH_USER_PROFILE__`) has the identical bug, the `authToken` global var (`6fcad7ad-…`) is reset-only and never written, and the docs don't cover this plugin. Fixed with a probe chain (`accessToken` → `authToken` → `token` → `wwLib.wwVariable.getValue('<pluginId>-accessToken')`). **If it recurs, the reliable route is the Xano plugin REST action `cd33cf33-e29f-4e8c-ac26-b997fe507ce7-request`, which attaches auth itself.** Rollback in `.claude/weweb_backups/pi_gates_pre_convergence_2026-08-16.md`.
- **Auth token carries NO access claims.** `auth/login` (ep 1) calls `create_auth_token` with `extras = {}`, expiration 86400 (24h). So access is read LIVE from the DB by `auth/me` (ep 3) on every call. `auth/me` is NOT server-cached (`cache.active:false`).
- **Implication:** stale post-purchase access is a WeWeb frontend problem (user object cached in a variable / localStorage and not re-fetched), NOT a Xano response-cache issue and NOT a token issue. Re-issuing the token does nothing for access — the fix is simply re-calling `auth/me` and overwriting the WeWeb user variable. Token expiry (24h) is the only token-related failure → forces re-login.
- **2026-08-13 — the 3-view free allowance is now SERVER-SIDE, in ep 230 `venue/pricing_intelligence_full`.** It previously existed ONLY in the WeWeb PI Locked Badge, so badge and payload could disagree: a user with 1 view saw an unlocked badge over a range-only payload because Xano had never heard of the allowance. ep230 now reads `total_vendor_views` and entitles when `forever_access_purchased || date_until_access >= today || total_vendor_views < 3`, checked in that order so a paying user is never labelled as being on the allowance. It also returns **`access_reason`** (`forever` | `active` | `free_allowance` | `lapsed` | `allowance_spent`) and **`free_views_left`** so the client can render a "2 free views left" badge without recomputing entitlement. Those two keys exist ONLY on ep230 — the public twin ep231 has no caller identity. Backups `ep230_pre_free_allowance_2026-08-13.xs` / `ep230_v2_free_allowance_2026-08-13.xs`.
- **CLIENT-SIDE ENTITLEMENT MATH IS THE BUG, NOT THE FIX.** Two formulas that looked reasonable and were both wrong: `total_amount_paid > 0` is a LIFETIME signal (a March 2-week buyer passes forever), and any date-only rule locks out lifetime buyers, whose `date_until_access` can be null while `forever_access_purchased` is true. Also `new Date('YYYY-MM-DD')` parses as UTC MIDNIGHT and expires people at the START of their last day — ep230 used to pad with `Date.parse(s + 'T23:59:59Z')` for that reason, **but this was REVERSED on 2026-08-16, see below**. The card should fetch `_full` for any logged-in user and render off `entitled` / `all_in.gated` / `access_reason`, computing nothing.
- **ep 150 `user/update_vendor_views` NOW OWNS THE COUNTER SERVER-SIDE (fixed 2026-08-13).** It used to write `total_vendor_views: $input.total_vendor_views|first_notempty:...` — an **absolute value supplied by WeWeb and stored verbatim**, with no server `+1` and no same-vendor guard. Harmless while it only drove a badge; a **paywall bypass** the moment ep230 started granting the free allowance off it (any logged-in user could PATCH themselves `total_vendor_views: 1` and hold free exact pricing forever). Now: the input is still accepted for WeWeb compatibility but **IGNORED**; the server does `math.add $views 1`; and both the counter and the `Clicks_on_Venue` bump are gated on `$input.vendor_id != $user_record.last_viewed_vendor_id`, so space-chip clicks and remounts no longer burn views or inflate ep119's `popular_desc`. The `db.get` was also moved from `$input.id` to `$auth.id` (it read a client-supplied id while writing to `$auth.id`, so passing someone else's id leaked their values onto your row). **Caveat: this dedupes CONSECUTIVE views, not distinct-vendors-ever — A→B→A counts twice.** Backups `ep150_pre_server_counter_` / `ep150_v2_server_counter_`.
- **ep 145 `userfreeviews/{user_id}` SECURED 2026-08-13.** Was `auth=false` writing `FreeViewsRemaining` to an arbitrary path `user_id` — and because `response = $user1` had no `output` list, an unauthenticated caller also got the **target user's entire row back, email included**, just by PATCHing an id. Now `auth="user"`, writes to `$auth.id`, path param ignored, response narrowed to `["id","FreeViewsRemaining"]`. Retained request history showed zero traffic. Backup `ep145_pre_auth_fix_2026-08-13.xs`.

- **2026-08-16 — PI FREE-ACCESS GAP CLOSED. `date_until_access` is now read at FACE VALUE (midnight), not end of day.** Root cause, confirmed in live request history (`5705038`): when a user burns their last free PDF view, WeWeb PATCHes **ep21 `user/update_record`** with `date_until_access: "<current ISO instant>"` — a deliberate "expire them now". `date_until_access` is a **`date` column**, so the time is truncated to `"2026-08-16"`, and ep230's `+ 'T23:59:59Z'` padding read that back as *entitled until midnight* → a free day of exact pricing (`entitled:true, access_reason:'active', all_in.gated:false`, real `total`/`per_guest` in the payload). ep230 now parses `s + 'T00:00:00Z'`, matching the dayjs `date()` idiom the WeWeb gates use. Backup `ep230_v3_pre_midnight_gate_2026-08-16.xs`. **Cost: a real buyer's access now ends at midnight ON the last day, not end of it** — accepted, since the navbar badge and Pricing Card always behaved that way.
- **The 8 PI conditional-rendering gates are CLIENT-SIDE (Venue Vendor Page `e49b4e74-…`). FINAL FORM 2026-08-16:** unlock = `forever==true || total_vendor_views<=3 || date_until_access > pluginFormulas['832d6f7a-…']['date']()`; lock = `forever!=true && total_vendor_views>3 && (date_until_access==null || date_until_access < …['date']())`. Elements: `PI Paid Badge` 09d017eb, `PI Headline Value Row` e884c95e, `PI Band Block` 910309ed, `PI Details Toggle` 7a8dc922, `PI Components` 94ab5295, `PI Badge Scale Legend` 8af7d6b1 (unlock); `PI Locked Badge` a526acc1, `PI CTA Block` d9c866c3 (lock). Three traps, all hit in one session: (1) **omitting `forever_access_purchased` locks out every lifetime buyer** whose date has passed — that, not the locked state, was the "empty locked panel"; (2) **`null < date()` returns FALSE in WeWeb's evaluator**, so a null `date_until_access` made the lock condition unreachable and no CTA ever rendered — a non-null past date compares fine, hence the explicit `==null` clause; (3) **the `<=3`/`>3` boundary MUST match ep230** — ep150 increments `total_vendor_views` BEFORE the panel loads, so on the Nth vendor the row already reads `views = N`, and the old exclusive `views < 3` gated the 3rd vendor one early.
